# Сезоны: соц-элемент к сборкам перков — лайк/дизлайк + комментарии

- **Раздел:** Прогресс — Сезоны/Перки, страница общей сборки — `/eft/progress/seasons/b/[code]`
- **Компонент:** блок реакций (лайк/дизлайк) + ветка комментариев под сборкой (нового нет) `~вывод`
- **Идея:** к расшаренной сборке билда добавить социальный слой — лайк/дизлайк и комментарии, чтобы под каждой сборкой копилось обсуждение.
- **Зачем / польза:** сборки перестают быть «одноразовой ссылкой» — появляется рейтинг удачных билдов и обсуждение по теме; удержание и повод возвращаться.
- **Как видит автор (2 варианта):**
  1. блок реакций+комментариев **внизу под самой сборкой** на текущей странице билда;
  2. **отдельная страница на сборку**, где копятся комментарии и ведётся обсуждение.
- **Ожидаемый результат:** под сборкой — счётчик лайков/дизлайков и тред комментариев.

> исходное сообщение (as-is, msg 370, часть про расширение):
> Теперь надо ее расширить и добавить социальный элемент лайк дизлайк и комментарий под каждой такой страницой сборки. Возможно внизу под самой сборкой или сделать отдельную страницу под саму сборку и там собирать все комментарии и своего рода вести обсуждение по теме.

## Разбор (2026-08-28)

**Главный вывод: это НЕ greenfield-бэкенд, а сборка из готового.** Разведка бэкенда показала — почти весь стек уже в проде и обкатан. Моя первичная оценка (`L`, «нужна БД/auth/модерация/антиспам») была неверной. Переоценка → `M`.

### Что уже есть (переиспользуем 1:1)
- **Auth:** `getMe()` (`src/lib/auth/me.ts`) — сессия Supabase (Twitch/Discord/email) → `profiles`. Готово.
- **Комментарии — полиморфный слой:** таблицы `entity_comments` + `entity_comment_votes` (`src/db/comments-ddl.ts`), ридер `src/db/entity-comments.ts`, полный API `src/app/api/eft/comments/{route,vote}.ts` (создать/список/мягко-удалить/скрыть + карма-порог), UI-компонент `<EntityComments>` — **drop-in**. Цели адресуются парой `type`+`id` из реестра `src/lib/comment-targets.ts`, FK на цель нет. Модерация (hide/soft-delete) и антиспам — внутри.
- **Лайки — прямой прецедент:** `weapon_builds.likes` (денорм-счётчик) + `weapon_build_likes` + toggle-API `src/app/api/eft/builds/like/route.ts`. Ровно шаблон для лайков сборки.
- **Антиспам:** `rateLimit(key,max,win)` (`src/lib/rate-limit.ts`, fixed-window upsert, fail-open) — уже висит на комментах (30/ч), голосах (200/ч), лайках (120/ч).
- **Модерация/репутация:** marked-rooms (`src/db/marked-rooms.ts`) — прецедент ledger'а репутации, если захотим награждать за популярные сборки.
- **Ключ сборки детерминирован:** `encodeBuild = [...ids].sort().join('.')` (`src/lib/season-points.ts`) — одинаковая комбинация перков в любом порядке даёт один код → одинаковые сборки естественно сходятся в один тред.

### Гоча ключевания (нашлась при разборе)
Raw-код сборки **нельзя** класть в `target_id` комментария как есть: реестр требует `TARGET_ID_RE = /^[a-z0-9][a-z0-9-]{1,64}$/` — **точки запрещены**, лимит ~66 символов, а код перков — с точками и ~100 символов (`average.polyphagia.sturdy-bones…`). Нужен короткий slug для сборки (как у `weapon_builds`, `/^[a-z0-9]{6,16}$/`).

### Развилки (нужно решение V4DYA — по ним пауза)
- **A. Лайк-ONLY vs лайк/дизлайк.** Вся текущая инфра — **однонаправленная** (и лайки сборок, и голоса комментов = только +1). Автор просит именно «лайк дизлайк». → либо (A1) лайк-only (макс. переиспользование, но теряем «дизлайк» из ТЗ), либо (A2) `value ∈ {+1,-1}` + два денорм-счётчика (маленькая новая таблица `season_build_reactions`, зеркалит `weapon_build_likes` + колонка value). **Реко: A2** — честит запрос малой ценой.
- **B. Ключ/хранение.** **Реко: B2** — лёгкая строка `season_builds(slug, code, season_slug, …counters)`, slug генерится из канон-кода, создаётся лениво при первом шаринге/реакции (зеркалит `weapon_builds`). Даёт slug↔code (нужно для «открыть сборку» из ленты модерации), дом для денорм-счётчиков лайков, и заодно решает развилку E.
- **C. Размещение: под сборкой vs отдельная страница.** У `/eft/progress/seasons/b/[code]` **уже есть** стабильный per-build URL → варианты автора смыкаются. **Реко: вариант 1** — блок реакций + `<EntityComments type="season-build" id={slug}>` под конструктором на той же странице. Новый роут не нужен.
- **D. Гейтинг записи (продуктовый вызов).** Текущие комментарии портала пишут **только платный тир «Оперативник»+** и модераторы (`canWriteComments`, `src/app/api/eft/comments/route.ts`). Наследуем ли этот пейволл для комментов сборок (консистентно + монетизация) или открываем всем залогиненным (больше вовлечения, но рассинхрон с остальным порталом)? Реакции — по прецеденту любой залогиненный, чтение публичное. **Нужен твой выбор.**
- **E. Мультисезонность.** Коды уникальны внутри сезона; при 2+ сезонах теоретически коллизии. Решается B2 (колонка `season_slug` + глобально-уникальный slug).

### Объём работ (при A2+B2+вариант 1)
1 новый DDL-модуль (`season-builds-ddl.ts`: `season_builds` + `season_build_reactions`) + RLS-SQL; новый тип цели `season-build` в `comment-targets(.server)`; серверный «ensure build row» (ленивый upsert code→slug); API реакций (клон `builds/like` с value); UI-обвязка на `/b/[code]`. Комменты-UI/API/модерация/rate-limit — **без изменений**. Миграция по канону `db:push → db:migrate-all → db:sql` (`/cta-backend`).

### Решения V4DYA (2026-08-28) — развилки закрыты
- **A → A2:** лайк/**дизлайк** (`value ∈ {+1,-1}` + два денорм-счётчика, таблица `season_build_reactions`).

Чтение публичное, реакции — любой залогиненный.
- **E:** решена B2 (`season_slug` + глобально-уникальный slug).
