# Keenetic Giga + Aeza: VPN-роутинг (AmneziaWG → VLESS/REALITY)

**Статус:** ✅ Работает. **Роутер — на AmneziaWG** (нативный интерфейс), **устройства — на Hysteria2 через Happ**. Попытка увести роутер на Hysteria2 через прокси-интерфейс Keenetic провалилась, причина найдена (§11). Провайдер душит **любой TCP+TLS** (VLESS на 443 и на 8443 одинаково), **UDP проходит свободно** → рабочий транспорт = **Hysteria2** (§10). VLESS оставлен запасным на случай сетей, где режут UDP. AmneziaWG держится в проде. **VLESS/XHTTP/REALITY поднят и проверен сквозным соединением** — осталось завести на клиентах.
**Дата:** 2026-09-06 / 07 (ночная сессия + разбор 07.09)
**Продолжать отсюда:** §6 «Что осталось сделать». Разбор починки — §4.

## 1. Что за задача

Весь **русский и локальный** трафик — через провайдера напрямую.
Весь **остальной** — через свой VPS в Стокгольме.
При падении туннеля — **killswitch**: доступ наружу закрывается, а не утекает с домашнего IP.

## 4. Что было сломано — разбор 07.09

Обе гипотезы прошлой сессии оказались **неверны**. Реальная причина одна, и она же объясняет всё.

### ✅ Блокер 1 (нужен XHTTP) — сделан

Inbound переведён на `"network": "xhttp"` + `xhttpSettings {path, mode}`.
`flow: xtls-rprx-vision` при XHTTP не применяется — убран и из сервера, и из ссылок (остался только на резервном TCP-порту 8443, где он уместен).

### ✅ Блокер 2 (соединение не встаёт) — причина: **маскировочный сайт**

**Не ключи, не версии, не sing-box.** Диагностика по шагам:

1. **Ключи сверены** — `xray x25519 -i <privateKey>` отдаёт ровно тот `PublicKey`, что записан в `pbk`. Гипотеза №1 опровергнута.
2. **Логи нашлись.** В блоке `log` не было путей к файлам → всё уходило в **journald**, а `/var/log/xray/error.log` физически не создавался. «Пустой лог» означал «смотрим не туда», а не «до VLESS не доходит». Смотреть: `journalctl -u xray`.
3. **Решающий тест** — xray-**клиент** подняли на самом VPS и постучались в собственный `443` с ключами из его же конфига. Соединение не встало → проблема на **сервере**, роутер и Happ ни при чём. Это сняло из подозреваемых весь клиентский стек разом.
4. **`realitySettings.show: true`** показал внутренности рукопожатия — и оказалось, что **REALITY-аутентификация проходит успешно**: сервер видит `AuthKey`, `ClientVer: [26 3 27]`, `ClientShortId` = наш `shortId`. Значит ключи, UUID и sid были в порядке всё это время.

Падало на следующем шаге — подмене сертификата с сайта-маскировки:

```
Server Hello: 1215   → в буфере осталось 2881
Change Cipher Spec: 6
Encrypted Extensions: 41
Certificate: 8273    → в буфере осталось 2834   ← не влезает
hs.c.isHandshakeComplete.Load(): false
```

`www.microsoft.com` отдаёт TLS-сообщение Certificate на **8273 байта** (длинная цепочка + OCSP + SCT). REALITY читает ответ сайта-маскировки в буфер около 4 КБ, целиком сообщение туда не помещается, рукопожатие не завершается — и клиент получает `EOF`.

**Проверено перебором, а не рассуждением:** восемь сайтов-кандидатов подставлены в конфиг и прогнаны сквозным соединением — **работают все восемь**, не работает только `www.microsoft.com`.

Выбран **`swdist.apple.com`**: TLS 1.3, HTTP/2, компактная цепочка, 87 мс от Стокгольма.
Почему не другие: **Cloudflare** — его SNI душат ТСПУ в РФ; **Google** — валт предупреждает, что на промо-тарифе IPv4 не заменить, а бан у Google означал бы пересоздание сервера. Apple — правдоподобный трафик с домашней сети (обновления macOS/iOS), банить нас ему незачем.

> ⚠️ **Правило на будущее:** сайт-маскировка для REALITY выбирается не по «солидности бренда», а по трём измеримым признакам — TLS 1.3, HTTP/2 и **короткая цепочка сертификатов**. `www.microsoft.com`, `yahoo.co.jp`, `www.nvidia.com` по третьему признаку не проходят.

## 5. Гочи — каждая стоила времени

1. **На встроенной памяти лежал Entware ЧУЖОЙ архитектуры (mipsel)** — `exec sh` падал с `exec format error`, а `opkg update` молча выполнялся как команда роутера. Лечится: положить `EN_aarch64-installer.tar.gz` в `storage:/install`, затем `opkg disk storage:/`.
2. **Панель Keenetic НЕ умеет форматировать в ext4** — в списке ФС только `SWAP`. Только `mkfs.ext4` из шелла (`opkg install e2fsprogs`).
3. **Keenetic кэширует ФС раздела.** После `mkfs.ext4` он продолжает считать раздел `vfat`, флешка не появляется в списке OPKG. **Нужна перезагрузка роутера.**
4. **`opkg disk <name> <url>` НЕ скачивает установщик.** Команда только назначает диск; URL игнорируется. Имя диска — `storage:/`, не `FlashStorage:Partition1`.
5. **KeeneticOS-SSH не поддерживает авторизацию по ключу** (только пароль). Dropbear из Entware ключ тоже не принял: `Exit before auth (user 'root', 0 fails)` при корректном `authorized_keys` (104 байта, права 600, home `/opt/root` подтверждён в `/etc/passwd`, `authorized_keys` есть в бинаре). **Причина не найдена** — работаем через веб-терминал ttyd.
6. **Кнопка «Пароль» в веб-терминале** вставляет пароль в командную строку, если приглашение уже `~ #`. Нажимать только на запросе `Password:`, иначе пароль светится в истории.
7. **DNS-маршрутизация NDMS не действует на устройства со своей политикой доступа** — только на «политику по умолчанию». Поэтому правило «Все AI сервисы» на ПК не влияло вообще.
8. **Ping-check на адрес внутри туннеля = замкнутый круг.** Адрес клиента `/32`, маршрут до `10.8.1.1` берётся из дефолта, дефолт снимается killswitch'ем при `fail` → ping-check не может пропинговать → вечный `fail`. Обход: статический маршрут `ip route host 10.8.1.1 Wireguard0`. Но сам ping-check в итоге **не заработал** (`status=fail`, счётчики `ok=0 fail=0` не растут) — **отвязан и удалён**, killswitch работает без него.
9. **`iplist.opencck.org` и `russia.iplist.opencck.org` — РАЗНЫЕ списки.** Основной домен отдаёт заблокированные в РФ сервисы (в `country=ru` — сети AWS, а не Яндекса). Российские сервисы — только на поддомене `russia.`.
10. **CORS у iplist нет** — браузером из панели не забрать. Обход: локальный HTTP-сервер на ПК с `Access-Control-Allow-Origin: *`, `fetch` со страницы awg-manager.
11. **Нативный диалог выбора файла недоступен для автоматизации** — загрузка файла в панель роутера требует рук V4DYA.
12. **WebCLI Keenetic глотает команды** (пустой ответ, поле не очищается). Надёжнее — прямой POST на `/rci/` из консоли браузера: `fetch('/rci/', {method:'POST', body: JSON.stringify([{...}])})`.
13. **⚠️ Сайт-маскировка REALITY с длинной цепочкой сертификатов ломает рукопожатие.** `www.microsoft.com` отдаёт Certificate на 8273 Б — не влезает в буфер REALITY, соединение рвётся с `EOF`. Симптом обманчив: выглядит как «неправильные ключи». Проверять кандидата **сквозным соединением**, а не глазами. Не годятся также `yahoo.co.jp`, `www.nvidia.com`.
14. **⚠️ Xray без путей в блоке `log` пишет ТОЛЬКО в journald.** `/var/log/xray/error.log` не создаётся вовсе, и его пустота ничего не доказывает. Целый заход диагностики ушёл на «лог пустой даже в debug». Смотреть `journalctl -u xray`; в конфиг добавлены `log.access` и `log.error` (каталог `/var/log/xray` — владелец `nobody`, под которым идёт служба).
15. **`realitySettings.show: true` — главный диагностический инструмент.** Печатает `AuthKey`, `ClientVer`, `ClientShortId` и пошаговый разбор рукопожатия. Сразу отвечает на вопрос «ключи не сошлись или сломалось позже». Включать при любой непонятной проблеме с REALITY, потом выключать.
16. **Проверять сервер xray-клиентом на самом сервере.** Клиент на VPS → собственный публичный IP → наружу. Одним тестом отсекается весь клиентский стек (роутер, sing-box, Happ, провайдер) — сразу видно, чья это половина.
17. **`pkill -f <шаблон>` через `ssh` убивает саму ssh-сессию** (exit 255): шаблон попадает в командную строку удалённой оболочки и матчит сам себя. Обход — `fuser -k <порт>/tcp` или скрипт-файлом.
18. **Happ на ПК работает в TUN-режиме с РАЗДЕЛЬНОЙ маршрутизацией** — часть адресов идёт в туннель, часть напрямую, независимо от настройки прокси. Поэтому «проверил свой IP — показывает домашний» ничего не доказывает: `icanhazip.com` отдавал реальный IP, а `cloudflare.com/cdn-cgi/trace` в ту же секунду — финский узел (`colo=HEL`). **Проверять несколькими сервисами**, иначе диагноз строится на артефакте правил маршрутизации.
19. **Замеры с ПК невалидны, пока на нём поднят Happ.** Маршрут до VPS уходил через `happ-tun` на чужой сервер, и VPS видел тесты с постороннего адреса. Мерить связь до нашего сервера — с телефона или при выключенном клиенте.
20. **Массовые ретрансмиты и `cwnd:1` в `ss` ≠ блокировка.** Ровно так же выглядит соединение, брошенное клиентом при переключении профиля VPN (TUN рвётся без FIN, сервер долбит в пустоту). Смотреть на `lastrcv`: сотни секунд тишины — это брошенная сессия, а не DPI.
21. **⚠️ Aeza с декабря 2025 сама блокирует VPN на своих серверах** по требованию РКН — рассылает тикеты «удалить в 24 часа, прислать скриншот», иначе отключение. Распространяется ли на Стокгольм — неизвестно. Риск провайдерский, не технический: сервер могут просто выключить. Держать в уме при вложениях в эту площадку.
22. **Проверка портов «снаружи» через `/dev/tcp` при поднятом TUN-клиенте ЛЖЁТ.** TUN принимает TCP-соединение локально, ещё не зная, дойдёт ли оно, поэтому «открыт» показывается даже для порта, где никто не слушает (проверено на 8080). Судить о доступности — по правилам `ufw` на сервере или с устройства без VPN.
23. **3x-ui 3.7 не пускает POST без CSRF-токена** (403 с пустым телом, в журнале ничего). Для автоматизации — не логин-форма, а **API-токен**: `x-ui setting -getApiToken`, дальше заголовок `Authorization: Bearer <токен>`. Заголовки `X-API-Token`/`Token` дают 404.
24. **Писать инбаунды прямо в `x-ui.db` бесполезно.** В 3.7 клиенты вынесены в отдельные таблицы (`clients`, `client_inbounds`), и вручную вставленные строки панель показывает в списке, но в конфиг Xray **не переносит** — порты не поднимаются. Заводить только через API/UI.
25. **3x-ui требует глобально уникальные `email` клиентов** между всеми инбаундами — это ключ учёта трафика. Один человек на трёх портах = три записи вида `V4DYA-443`, `V4DYA-30982`, `V4DYA-8443`. Дубликат отвергается с `Duplicate email`.
26. **`tgId` в API — число, не строка** (`cannot unmarshal string into Go struct field .0.tgId of type int64`).
27. **Включать ufw по SSH — со страховкой.** `nohup sh -c "sleep 180; ufw --force disable" &` перед `ufw enable`; если доступ не потерян — снять по PID. Иначе одна опечатка в правилах = потеря сервера.
28. **⚠️ Свежий Happ не принимает `insecure` — требует `pinnedPeerCertSha256`.** Ошибка при подключении: «The feature allowInsecure has been removed and migrated to pinnedPeerCertSha256». Для самоподписанного сертификата в ссылку добавляется `pinSHA256=<отпечаток>`; взять его — `openssl x509 -in cert.pem -noout -fingerprint -sha256`. Старые версии клиента новые ссылки тоже не поймут — обновлять обязательно.

30. **NAT-правило `PREROUTING -i <внешний>` не действует на трафик, идущий по петле.** Проверка прыжков по портам с самого сервера давала `timeout: no recent network activity` при исправном правиле — пакет на собственный публичный IP идёт через `lo` и до `PREROUTING` внешнего интерфейса не доходит. Лечится отдельным правилом в `OUTPUT` **с ограничением по адресу назначения** — иначе перехватишь UDP-трафик пользователей на те же порты.
31. **Подписки Happ на диске зашифрованы** (`%LOCALAPPDATA%\Happ\subs.db`, таблица `subscriptions`, поле `data`). Прочитать чужие настройки, чтобы скопировать рабочую схему, не выйдет. Что реально работает — видно по сети: `Get-NetTCPConnection` показывает адрес и порт живого туннеля.
32. **Поле REALITY называется `dest`, а не `target`.** Прошлая сессия записала `target` — валидацию `xray run -test` это проходит (лишние поля игнорируются молча), но полагаться на такое нельзя. В новом конфиге — `dest`.

## 10. Hysteria2 — ответ на замедление VLESS

Развёрнут 07.09 после того, как §9 доказал: душат TCP-поток VLESS, а не адрес и не маршрут. Логика простая — **уйти с TCP на UDP**, который у провайдера не под таким прицелом.

Подтверждение из разведки: рабочих протоколов в РФ на сентябрь 2026 осталось три — VLESS+Reality, AmneziaWG и Hysteria2 (чистые WireGuard, OpenVPN, Trojan, Shadowsocks не проходят). Hysteria2 работает поверх **UDP/QUIC с обфускацией Salamander**, и источники отдельно отмечают: там, где TCP на 443 интенсивно анализируется, он даёт выше скорость и меньше разрывов.

- окна QUIC расширены до 8/20 МБ под высокую скорость

Пароли и obfs — в `/root/vless-params.txt` (`HY2_*`). В валт не выносим.

1. `POST /api/singbox/tunnels` с телом `{"links": "<ссылка строкой>"}` — в ссылке **`insecure=1`**, НЕ `pinSHA256`
2. `POST /api/singbox/control` `{"action":"restart"}` — перечитать конфиг
3. `DELETE /api/access-policies/permit?name=Policy3&interface=<лишний>` — оставить в политике ОДИН выход
4. `POST /api/access-policies/assign` `{"mac":"...","policy":"Policy3"}` — привязать устройства
5. Проверка: `GET /api/singbox/tunnels/test/ip?tag=<тег>` → должно быть `ipChanged: true`

⚠️ Туннель **не переименовывать**: имя зашито в привязку прокси-интерфейса Keenetic.

### 🔴 Три прибора, которые врали (стоили часа диагностики)

1. **Счётчики правил NAT считают ТОЛЬКО первый пакет потока.** Дальше соединение обслуживает conntrack мимо правила. При живом трафике счётчик стоит на месте. По нему был сделан вывод «трафик устройств до сервера не доходит» — **неверный**. Для измерения идущего трафика брать счётчики clash-API роутера (`downloadTotal`/`uploadTotal`) или интерфейса.
2. **Вход sing-box типа `mixed` слушает `127.0.0.1`** → в списке соединений clash **все** записи с источником `127.0.0.1`, реальный IP устройства не виден в принципе. Вывод «это проба роутера, а не телефон» тоже был неверным.
3. **`connected` в awg-manager не означает идущий трафик.** Туннель поднимается по требованию: без трафика сессий нет, но проба проходит. Обратное тоже верно — `connected=false` сразу после перезапуска не значит поломку.

Общее правило: **прежде чем делать вывод «трафика нет», проверить, что прибор вообще способен этот трафик увидеть.**

## 12. Запас прочности сервера — измерено, не прикинуто

Вопрос: выдержит ли VPS весь дом (PS5, игровой ПК, телефоны) на играх и YouTube.

**Нагрузочный тест 07.09** (поток 30 с через живой Hysteria2):

```
прокачано 700 МБ за 21 с   =  266 Мбит/с
CPU процесса hysteria:        33% средн, 40% пик
load average:                 0.58
память:                       547 МБ из 3916
→ ~12% одного ядра на каждые 100 Мбит/с
```

Оценка занижена в нашу пользу: тест гонял клиента и сервер на одном ядре, в бою сервер работает один.

**Вывод: процессор не узкое место.** По линейной оценке ядро вытянуло бы ~800 Мбит/с — раньше упрётся канал 300 Мбит/с. Память не задействована (0.5 ГБ из 4). Трафик у Aeza безлимитный, но **промо-тариф отдельно не проверялся — сверить в панели**.

### Что канал 300 Мбит/с реально вмещает

| нагрузка | потребление |
|---|---|
| YouTube 4K, один поток | ~25 Мбит/с |
| YouTube 1080p | ~8 Мбит/с |
| онлайн-игра (сам матч) | 0.1–1 Мбит/с |
| загрузка игры на PS5 | съест всё, что дадут |

Двенадцать одновременных 4K-потоков — предел. Реальный дом столько не создаёт.

### 🔴 Настоящие ограничения — не мощность

1. **Задержка.** RTT до сервера ~50 мс (замерено в `ss`). Для соревновательных шутеров это ощутимо. **Игровой трафик PS5 и ПК через туннель гнать не надо** — только то, что без него не работает. Держать логику как с RU-списком: направляем в туннель выборочно, а не всё подряд.
2. **Загрузки игр.** 100 ГБ на скорости канала — 45 минут, в которые всё остальное будет тормозить. Качать напрямую.
3. **Риск площадки.** Aeza отключает VPN-серверы по требованию РКН (§4). Чем заметнее трафик, тем выше шанс попасть под раздачу. Это довод в пользу выборочной маршрутизации, а не только вежливости.

### Диагностика доступности снаружи: iwtsy.com

Распределённая проверка «виден ли сервер из России» с узлов у разных операторов. Различает: порт закрыт (RST) → проблема на сервере · TCP есть, баннера нет → активная фильтрация · полная недоступность → блокировка IP.

Вводить: **`2.56.121.14`** и порт. Полезные проверки — **22** (эталон: этот порт точно рабочий), **443** и **30982**.

**Результат проверки 07.09:** порты 22, 443, 8443 доступны из РФ, **порт 30982 — в бане**. То есть отдельные порты у операторов действительно блокируются списком; VLESS-инбаунд на 30982 можно считать мёртвым.

⚠️ **Проверяет TCP.** Наш основной транспорт — Hysteria2 на UDP, его этим сервисом не проверить. Ценность в другом: покажет, не занесён ли сам IP в чёрные списки у операторов, и даст объективную картину по Fullkamen и другим сетям.

## 13. 🔴 ПОЧЕМУ РОУТЕР НЕ ПОШЁЛ НА HYSTERIA2 — причина найдена

Двое суток «подключено, но ничего не грузится» на устройствах за роутером. Причина оказалась в одной строке конфига AmneziaWG:

```
dns: 1.1.1.1, 8.8.8.8
```

Роутер **раздаёт клиентам публичные DNS**. Дальше всё сходится:

- **на AmneziaWG работает** — это настоящий сетевой интерфейс, UDP-запросы к 1.1.1.1/8.8.8.8 идут как есть
- **через прокси-интерфейс Keenetic (`Proxy*` → SOCKS → sing-box) НЕ работает** — это мост поверх SOCKS, UDP через него толком не ходит
- нет DNS → Android помечает сеть «Wi-Fi без доступа в Интернет» и уходит на мобильный
- в логах это видно прямо: единственное соединение телефона — к `8.8.4.4`, висит, `dl` не растёт

**Почему я долго не видел:** мои проверки шли через `curl --proxy socks5h`, где имена резолвит сам sing-box по TCP. У меня проходило ВСЁ (HTTP/80, HTTPS, `generate_204`, DoT/853, объём данных) — а телефон в это же время не мог сделать простейший UDP-запрос.

### Вывод

Связка **Keenetic Proxy + sing-box непригодна как выход политики для обычных устройств**: она не носит UDP, а без UDP нет DNS. Для сетевого уровня годится только нативный интерфейс — **AmneziaWG**.

Раскладка, к которой пришли:

| уровень | транспорт | статус |
|---|---|---|
| роутер, вся сеть | **AmneziaWG** (нативный `nwg0`) | ✅ работает |
| ПК, телефон лично | **Hysteria2** через Happ | ✅ работает |
| русские сайты | напрямую, 1448 подсетей | ✅ проверено |

### Цена ошибок этой ночи (для честности)

Дважды сеть оставалась без интернета из-за моих действий: пересборка моста NDMS уронила `Proxy2` без возможности поднять его перезапуском, а пересоздание туннеля сменило интерфейс на `Proxy0`, оставив политику указывать на несуществующий `Proxy2`.

## 14. AmneziaWG 3.x — почему НЕ поставлен

Проверено 07.09:

- **на сервере уже стоит `amneziawg-tools 3.1.20260812`** и модуль ядра той же версии — движок новейший
- **в конфиге сервера параметры только 1.0**: `Jc/Jmin/Jmax/S1/S2/H1–H4`. Полей 3.x (`I1–I5` — сигнатурные пакеты) нет
- **на роутере туннель работает на `backend: nativewg`** — нативном WireGuard Keenetic. Его набор параметров: `jc, jmin, jmax, s1, s2, s3, s4, h1–h4`. **`I1–I5` он не принимает**
- awg-manager схему `i1–i5` знает (`api.SignaturePacketsDTO`), но только для собственного движка, не для нативного

**Вывод: «включить AWG 3» — это не правка конфига, а смена движка туннеля на роутере.** Обфускация должна совпадать с обеих сторон: включить `I1–I5` только на сервере = положить туннель и всю домашнюю сеть.

### Что реально можно, по возрастанию риска

1. **`S3`/`S4`** — нативный движок их принимает (сейчас `s3=0, s4=0`). Поколение 2.0 вместо 1.0, малый шаг, малый риск
2. Перевести роутер на **управляемый движок awg-manager** — тогда доступны `I1–I5`, но теряется нативность, а именно она сегодня и спасла
3. Оставить как есть: AWG 1.0 работает, а основную стойкость даёт Hysteria2 на устройствах

⚠️ Любой из вариантов — **только при бодрствующем V4DYA**: ошибка оставляет без интернета весь дом, включая семью, и обрывает мой доступ к роутеру.
