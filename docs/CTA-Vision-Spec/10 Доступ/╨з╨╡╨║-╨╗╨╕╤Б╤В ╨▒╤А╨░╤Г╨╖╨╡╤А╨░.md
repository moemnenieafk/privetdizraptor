# Чек-лист браузера

Применимо, когда [[Как Google банит Gemini|слой 2]] чистый: API работает, аккаунт в поддерживаемой стране, а вкладка отдаёт заглушку.

> [!tip] Почему расхождение
> API-ключ ходит голым HTTPS-запросом. Веб-приложение отдаёт наружу ещё пять сигналов, которых у API нет в принципе. Отсюда «API ок, браузер нет».

## По убыванию вероятности

1. **WebRTC.** STUN отдаёт реальный IP мимо туннеля. Проверка — `ipleak.net`: если в блоке WebRTC российский адрес, это ответ. Лечение: `chrome://flags` → WebRTC IP handling → *Disable non-proxied UDP*, либо расширение WebRTC Leak Prevent.

2. **Geolocation permission.** Если `google.com` когда-то получил доступ к геолокации, Chrome отдаёт результат Wi-Fi-скана — точнее любого IP. Настройки сайтов → `google.com` и `gemini.google.com` → Местоположение → **Блокировать**. Именно блокировать, не «спрашивать».

3. **Cookies.** `NID`, `1P_JAR`, `CONSENT` несут прошитый регион и переживают смену IP. Полная очистка по всем доменам `google.com`, либо чистый профиль.

4. **QUIC.** `chrome://flags/#enable-quic` → Disabled, либо резать UDP/443 на клиенте.

## Диагностика по симптому

| Симптом | Причина |
|---|---|
| «not available in your region» | IP / гео-сигнал → пункты 1–4 |
| Бесконечный спиннер | не завёрнут `proactivebackend-pa.googleapis.com` |
| Редирект на google.com или логин | cookies / состояние сессии → пункт 3 |

## Быстрый тест

Свежий профиль Chrome — **не инкогнито**, оно наследует часть флагов. VPN включён. Открыть `ipleak.net`, убедиться что IP, DNS и WebRTC показывают одну страну. Только потом логиниться и открывать Gemini.

- Работает в чистом профиле → дело в состоянии старого профиля, сеть не трогать
- Всё чисто, заглушка висит → IP помечен как datacenter, лечится WARP-плечом
