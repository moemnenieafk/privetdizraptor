# SPEC: как рисовать карты ЦТА, чтобы движок и маркеры не сломались

Документ описывает контракт между отрисованным SVG и движком карты. Соблюдение
контракта означает, что любую карту можно подменить файлом без единой правки
кода, конфига и слоя маркеров.

> **Ревизия от 29.07.2026.** Переписаны §1 (были перепутаны названия осей),
> §6 и §8 (GraphQL API tarkov.dev не отвечает), добавлен §9 про растровый
> референс. Сводка — в конце документа.

**Где живёт реализация:** `src/data/eft-map-config.ts` (конфиг 13 карт),
`src/components/features/maps/MapViewerClient.tsx` (сборка CRS и рендер).
Прежде чем менять контракт, читать оба файла — они рабочие и сверены 23.06.2026.

## 1. Холст, масштаб, проекция

### Как это работает сейчас

Движок строит кастомный `L.CRS.Simple`. Игровые координаты маркера подаются как
`latLng(z, x)` — то есть `x` идёт в долготу (горизонталь), `z` в широту
(вертикаль). Дальше применяется поворот на `coordinateRotation`, затем
`L.Transformation(transform[0], transform[1], -transform[2], transform[3])`.
Подложка кладётся `imageOverlay` по тем же `bounds` через тот же конвейер —
поэтому картинка и маркеры совмещаются автоматически.

**`transform` — не «метры в пиксели viewBox».** Он отображает в собственное
CRS-пространство Leaflet. На Customs подложка занимает в нём 255.6 × 130.0
единиц при viewBox 1062.5 × 535.2. Мерить его результат линейкой viewBox
бессмысленно — соотношение сторон совпадает (1.97 против 1.985), абсолютные
числа нет.

### Соответствие осей

**Ширина холста отвечает игровой оси X, высота — оси Z.**

Проверено по четырём независимым источникам: `ll(p) = [p.z, p.x]` в живом коде,
`SpawnPointParams` из базы SPT, `Bounds` из DynamicMaps, `bounds` из maps.json.
Совпадение на пяти картах из пяти.

В предыдущей ревизии этого документа было записано обратное («при rotation 180
ширина отвечает оси Z»). Размеры холстов в той таблице при этом были верные —
перепутаны только подписи осей. Отрисованное по старой таблице перерисовывать
не нужно.

### Развилка при перерисовке

Существующие SVG Shebuka нарисованы в кадре, повёрнутом относительно игрового,
и `transform` под них откалиброван. Перерисовывая карту, выбираешь одно из двух:

**Вариант А — остаться в текущей схеме.** Рисуешь холст в той же ориентации,
что у Shebuka, и калибруешь `transform` под новые размеры. Код не трогается,
меняются четыре числа на карту в `eft-map-config.ts`. Дешевле.

**Вариант Б — перейти в игровой кадр.** Рисуешь X по горизонтали, Z по
вертикали, Z растёт вверх, холст размером ровно с `bounds`. Тогда в конфиге
ставится `coordinateRotation: 0`, `transform` вырождается в тождественный, и
проекция сводится к переносу с отражением по Y:

```
svgX = (gameX - bounds.xMin) * viewBoxW / boundsWidth
svgY = (bounds.zMax - gameZ) * viewBoxH / boundsHeight
```

Плюс варианта Б — исчезает исключение «при 90/270 оси меняются местами»
(Factory и Labs у Shebuka развёрнуты на 90°), и все карты живут в одном кадре.
Минус — конфиг и калибровка переделываются целиком, смешивать варианты внутри
одного набора нельзя.

**Вариант выбирается один раз на весь набор, не по карте.**

### Размеры холста

`1 единица SVG = 1 игровой метр`. `viewBox` начинается с `0 0`.

## 2. Структура групп

Обязательный минимум — корневая группа уровня земли с `id`, совпадающим с полем
`svgLayer` в конфиге (по умолчанию `Ground_Level`):

```xml
<svg viewBox="0 0 1070 541" xmlns="http://www.w3.org/2000/svg">
  <style id="style_common"> ... </style>

  <g id="Ground_Level">
    <g id="Schematic">          <!-- читаемая абстрактная база -->
      <g id="Ground">   <path class="land" .../> </g>
      <g id="Roads">    <path class="road_tarmac road_medium" .../> </g>
      <g id="Buildings"><path class="building" .../> </g>
    </g>
    <g id="Detail">             <!-- спутниковая детализация, LOD -->
      <g id="Rubble"/>  <g id="Vegetation"/>  <g id="Debris"/>
    </g>
  </g>

  <g id="Underground_Level"> ... </g>
  <g id="Second_Floor"> ... </g>
</svg>
```

Имена этажей должны совпадать с `layers[].svgLayer` в конфиге. Существующие
значения: `Ground_Level`, `Underground_Level`, `Second_Floor`, `Third_Floor`,
`Fourth_Floor`, `Fifth_Floor`, а для Factory — `Basement`, `Ground_Floor`,
`Second_Floor`, `Third_Floor` (четыре этажа, не два).

Этаж выбирается по игровой высоте `y` маркера через `heightRange` (уровень земли)
и `layers[].height` (остальные). Рисуешь этаж — держи в голове его высотный
интервал, иначе маркеры уедут не на тот слой.

Высотные интервалы Factory по DynamicMaps: `Basement` −100…−1,
`Ground_Floor` −1…3, `Second_Floor` 3…6, `Third_Floor` 6…100. Нижний уровень
там называется `Tunnels` — при переносе свести к одному имени, иначе выбор
этажа вернёт id, которого в файле нет.

## 3. Разделение «абстрактный / спутниковый»

Это ключевое решение для гибридного стиля. Две сестринские группы внутри каждого
этажа, а не один смешанный слой:

- `#Schematic` — силуэты зданий, дороги, границы, вода, рельеф. Это то, что
  читается на 360px шириной экрана. Плотность низкая, формы обобщённые.
- `#Detail` — щебень, растительность, разметка, текстурные штрихи, тени объёма.
  Это то, что даёт «спутниковость». Плотность высокая.

Зачем разделять: `#Detail` — это 60–80% веса файла. Разделив, можно гасить его
на мелком зуме через CSS без второго файла:

```css
.map-svg[data-lod="low"] #Detail { display: none; }
```

и не тащить 250 КБ путей, которые на зуме 1 всё равно схлопываются в кашу.
Порог переключения — примерно когда 1 единица SVG становится меньше 1 CSS-пикселя.

Второе преимущество: на `#Detail` можно навесить `opacity` слайдером в UI —
получается «прозрачность спутника», знакомая по картографическим сервисам, и это
реальная фича, а не декор.

## 4. Словарь классов

Стилизация только через классы, никаких `fill` в атрибутах.

**Заливки:** `land` `trees` `water` `rock` `gravel` `wood` `cement` `tarmac`
`building` `floor` `locked` `structure` `misc`

**Обводки:** `road_tarmac` `road_gravel` + модификатор ширины
`road_small` (5) / `road_medium` (8) / `road_large` (12), `railroad` (dasharray 6,
ширина 3), `powerline` (dasharray 6,6), `fence` (1), `map_border` (2)

**Смысловые:** `danger` / `danger_small` (опасные зоны), `stairs` (лестницы),
`shadow` (drop-shadow фильтр), `wall`

Для новых собственных категорий — префикс `cta_`, чтобы не конфликтовать при
слиянии: `cta_loot_zone`, `cta_sniper`, `cta_choke`, `cta_outline`.

## 5. Блок стилей

Каждый файл обязан содержать ровно один:

```xml
<style id="style_common"> ... </style>
```

`id` именно такой — на него завязан батч-скрипт подмены палитры. Внутри — только
токены, никаких HEX:

```css
.land{fill:var(--map-terrain)}
.building{fill:var(--map-building)}
.stairs{fill:var(--primary)}
.powerline{fill:none;stroke:var(--primary);stroke-width:2;stroke-dasharray:6,6}
```

**Критично:** `var()` внутри SVG работает только если SVG инлайнится в DOM.
Через `<img src>` или `background-image` каскад не проходит, и карта станет
чёрной. Читать файл в Server Component и отдавать через `dangerouslySetInnerHTML`,
либо SVGR на билде. Сами токены `--map-*` объявлять в `globals.css` как настоящие
CSS custom properties — Tailwind v4 не видит содержимое `.svg` при tree-shaking.

Токены, которых в наборе пока нет и которые нужно объявить:
`--map-floor`, `--map-structure`, `--map-wall`, `--map-misc`.

## 6. Чего в файле быть не должно

- **Текстовых подписей.** Топонимика живёт в `labels.json` (303 подписи с
  позицией, поворотом и кеглем) и рисуется UI-слоем. Иначе не будет ни
  локализации, ни масштабирования шрифта, ни поиска по названиям.
- **Растровых вставок.** `<image>` убивает векторность и раздувает файл.
- **Инлайновых `fill`/`stroke`** мимо классов.
- **`id` на отдельных path.** `id` только на группах — это точки монтирования.
  На фигурах — классы.
- **Маркеров.** Выходы, спавны, лут, замки приходят слоем поверх карты, по
  игровым координатам.

### Откуда берутся маркеры

GraphQL API `api.tarkov.dev` не отвечает и не восстановится. Источники сейчас:

| Что | Источник |
|---|---|
| Выходы, запертые двери, рубильники | `mpstark/SPT-DynamicMaps`, `Resources/Maps/*.jsonc` |
| Спавны, боссы, лут, ключи | `sp-tarkov/server`, `project/assets/database/locations/{map}/base.json` |
| Топонимика | `labels.json` из пака |

По DynamicMaps на десять карт приходится 320 маркеров: 188 запертых дверей,
117 выходов, 15 рубильников — плюс 254 подписи и 32 слоя с высотными объёмами.

Координаты в DynamicMaps лежат как `Position.x`, `Position.y` (плоскость) и
`Position.z` (высота). При переносе переименовывать в игровые оси: `x` → X,
`y` → Z, `z` → высота. Иначе высота попадёт в горизонталь.

У `exits` в базе SPT координат нет — только `Name`, `EntryPoints` и тайминги.
Позиции выходов берутся только из DynamicMaps. Ледокола в DynamicMaps нет.

## 7. Оптимизация перед коммитом

Дефолтный пресет SVGO уничтожает карту: срезает `id` групп и склеивает пути.
Рабочий конфиг лежит в `scripts/svgo.config.mjs`. На существующем наборе он даёт
−20…−36% без потери структуры.

Целевой вес после gzip — до 60 КБ на карту. Для сравнения, текущий набор:
Factory 7 КБ, Woods 44 КБ, Customs 46 КБ, Streets 85 КБ, Shoreline 101 КБ.
Shoreline за порогом — именно поэтому `#Detail` должен быть отделяемым.

## 8. Порядок работы над картой

1. Выгрузить растровый референс: `node scripts/fetch-tiles.mjs --map {key}`
   (см. §9). Дополнительно `raster/{key}-3d.jpg` из пака — для чтения объёма
   зданий.
2. Выставить холст по таблице из §1 согласно выбранному варианту (А или Б).
   Для Interchange, Reserve и Woods сверить с собственной геометрией.
3. Нарисовать `#Schematic`, проверить читаемость на 360px.
4. Нарисовать `#Detail` отдельной группой.
5. Наложить подписи — проверить, что они попадают на осмысленные объекты. Если
   подпись висит в пустоте, значит форма не нарисована или холст сдвинут.
   Оверлеи из пака предварительно починить, см. ниже.
6. Прогнать SVGO с конфигом из пака.
7. **Проверка на выходах.** Подменить подложку в дев-сборке и посмотреть, легли
   ли `Extract`-маркеры на нарисованные выходы. По варианту А при этом почти
   наверняка потребуется подстройка `transform` в `eft-map-config.ts`.

Шаг 7 — единственная настоящая проверка. Если выходы совпали, совпадёт всё
остальное.

### Оверлеи подписей из пака нерабочие

`labels/overlays/*.svg` в паке пишут сырые игровые координаты прямо в `x`/`y`
при `viewBox`, начинающемся с нуля. Всё отрицательное оказывается за холстом —
примерно 190 подписей из 303 не видно:

| Карта | вне холста |
|---|---|
| Interchange | 55 из 77 |
| Streets | 28 из 46 |
| Reserve | 24 из 27 |
| Lighthouse | 21 из 22 |
| Customs | 17 из 24 |

Перед использованием пересобрать с переносом в координаты холста. Знак поворота
подписи при этом инвертируется — отражение оси Y меняет направление вращения.

## 9. Растровый референс

`scripts/fetch-tiles.mjs` качает и сшивает тайловые пирамиды с
`assets.tarkov.dev`. Конфигурация карт тянется из `maps.json` the-hideout, а не
хардкодится.

```bash
node scripts/fetch-tiles.mjs --list
node scripts/fetch-tiles.mjs --map customs
node scripts/fetch-tiles.mjs --map icebreaker --zoom 4 --layers 06_infirmary
```

Тайлы есть у **всех десяти** карт, а не только у Labs, Labyrinth и Icebreaker:

| Карта | зумы | слоёв |
|---|---|---|
| customs | 2–6 | 5 |
| reserve | 2–6 | 6 |
| ground-zero | 1–6 | 4 |
| factory | 1–6 | 4 |
| icebreaker | 1–5 | 16 |
| the-lab | 2–6 | 3 |
| interchange, the-labyrinth | 1–6 | 1 |
| shoreline, woods | 2–6 | 1 |

Растр послойный по этажам и происходит из того же координатного пространства,
что и движок — в отличие от плоских `-2d.jpg` сторонних авторов.

### Что ломается при наивной сшивке

- **Цвет.** Тайлы приходят вперемешку в RGBA, RGB, палитре и однобитном
  формате с прозрачностью через `tRNS`. Мозаика перенимает интерпретацию
  первого тайла: если он серый, вся карта уедет в чёрно-белое с альфой,
  обрезанной на 173. Ошибка молчаливая — файл валидный, размеры верные.
  Каждый тайл приводить к sRGB + alpha **до** сшивки.
- **Размер тайла.** `tileSize` в конфиге — параметр отрисовки Leaflet, а не
  размер файла. У Лаборатории там 175 при реальных 256; счёт по 175 сдвинет
  всё на 46%. Брать из файла.
- **Регистрация слоёв.** Резать все слои карты по общему bbox, иначе этажи
  разъедутся друг относительно друга.
- **Сеть.** Часть прокси отдаёт 403 на программные запросы, пропуская curl.
  В скрипте обработано автопереключением.
- **Пределы форматов.** WebP не умеет стороны длиннее 16383 px. PIL не
  вытягивает кодирование холстов свыше ~200 Мпикс. Скрипт на sharp/libvips
  стримит и на больших зумах уходит в PNG.

### Отдельные случаи

**Ледокол.** `bounds` в исходных данных скопированы с Завода
(`[[77,-64.5],[-65.5,67.4]]`, соотношение 1.08) при реальном корпусе 1856 × 8192
(соотношение 0.23). `transform` анизотропный — `[2.0, 125.0, 3.5, 91.0]`,
единственная такая карта. Размер холста выводить из растра, не из `bounds`.
Плюс опечатка в пути слоя апстрима: `05_storage_ecurity`, без `s`. Исправленный
путь отдаёт 404, опечатку надо тащить как есть. И высоты слоёв 05 и 06
перекрываются на 0.01 м — выбор этажа там зависит от порядка в массиве, а не от
высоты.

**Лаборатория.** `minZoom` равен 2, на единице тайлов нет.

### Лицензии

`svg/` и `svg-nightfall/` — CC BY-NC-SA 4.0 (Shebuka), NC конфликтует с
подписками. Растровые тайлы и `raster/*.jpg` лицензий не публикуют. И то и
другое годится как референс форм и координат, но не как основа для обводки и
не для поставки в прод.
