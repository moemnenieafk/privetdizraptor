# Модель стоимости арена-валют (GP, Лега)

Модуль: `src/lib/arena-currency.ts` · типы: `src/types/arena-currency.ts`

## Проблема

GP-монета и Лега-медаль зарабатываются в Arena и переносятся в Тарков, где на них
торгует Реф. За рубли, евро и доллары их купить нельзя, поэтому рыночной цены у них
нет — есть только курс обмена, и задаёт его ассортимент Рефа, а не сама валюта.
Меняется ассортимент — меняется курс при неизменной монете.

Отсюда следствие, на котором держится вся модель:

> **Курс монеты — не число, а функция объёма.**

Первые монеты уходят по лучшей сделке, следующие — по второй, и так далее, и каждая
сделка ограничена лимитом покупок за сброс. Спрашивать «сколько стоит GP» без указания
объёма так же бессмысленно, как спрашивать цену акции без указания лота.

## Формула

Для каждого предложения Рефа `i`, оплачиваемого **только** монетами:

```
rate_i     = V_i / g_i          курс: рублей за монету
capacity_i = g_i · L_i          монет по этому курсу за сброс
```

`V_i` — рыночная стоимость награды, `g_i` — монет за покупку, `L_i` — лимит покупок.
Ступени сортируются по `rate` по убыванию — получается кривая предложения.

**Стоимость первых n монет:**

```
cum(n) = Σ_i  min( max(n − Σ_{j<i} capacity_j, 0), capacity_i ) · rate_i
```

**Производные:**

```
MV(n) = rate ступени, на которую попала n-я монета     предельный курс
AV(n) = cum(n) / n                                     средний курс
```

`MV` отвечает на «сколько стоит следующая монета», `AV` — на «во сколько в среднем
обошлась каждая, если потрачено n». На карточке имеет смысл показывать оба.

**Лега** выводится вычитанием из смешанных предложений:

```
lega_i = ( V_i − cum(g_i) ) / m_i
Лега   = median_i  lega_i
```

Медиана, а не среднее: выборка мала, один выброс её перекосит.

## Почему нельзя решать систему уравнений

Соблазн очевиден — два смешанных предложения дают систему с единственным решением:

```
150·x + y = 1 720 000     (кейс для вещей)
220·x + y = 1 748 999     (оружейный кейс)
→ x = 414 ₽,  y = 1 657 859 ₽
```

Математически безупречно и экономически бессмысленно: 70 лишних монет во втором
предложении добавляют к награде всего 28 999 ₽, тогда как отдельно монета уходит за
14 444 ₽. Прайс Рефа свёрстан вручную, линейной зависимости между числом монет и
ценой награды в нём нет. Решать его как линейную алгебру — значит получить точный
ответ на неправильно поставленный вопрос.

## Вердикт по предмету

Наивное «награда дороже монет» всегда даёт «выгодно», потому что сравнивает
предложение само с собой. Правильная база — **альтернативная стоимость**: сколько те
же монеты принесли бы, потрать их на что-то другое.

```
alt(g)  = cum(g) по кривой БЕЗ этого предложения
surplus = min(цена по остальным маршрутам) − alt(g) − m·Лега
```

Все маршруты приводятся к одной шкале: фиатные (рубли, евро, доллары) — по `priceRUB`
из зеркала, арена-маршрут — по `alt(g) + m·Лега`. После этого способы получить предмет
сравнимы напрямую, и карточка может честно сказать, где дешевле.

Показательный пример на живых данных: Powermag за 16 монет выглядит безобидно, пока не
посчитаешь, что те же 16 монет на верхних ступенях кривой стоят ~148 тысяч. Наивная
модель назвала бы его нормальной сделкой.

## Подключение к данным

Модуль `arena-currency.ts` намеренно чистый: внешних вызовов не делает и принимает
`ArenaOffer[]` от вызывающей стороны. Цепочка:

```
tarkov.dev ──синк──> barters (зеркало) ──getArenaOffers()──> calcGpCurve()
                                                          └─> calcLegaValue()
                                                                    │
                                        GET /api/eft/arena-rates ───┘
```

- `src/db/arena-offers.ts` — собирает предложения Рефа из зеркала, отбрасывает
  обмены с примесью обычных предметов, считает стоимость награды. Комиссия — через
  `calcFleaFee` из `src/lib/barter-calc.ts`, своей формулы модуль не заводит.
- `src/app/api/eft/arena-rates/route.ts` — публичная ручка с `rateLimit` по IP,
  параметры `basis` и `level`, кэш на час через `memoTTL` + `s-maxage`.

Поле `barters.buy_limit` (лимит покупок за сброс) добавлено в схему и в
`src/db/barters-crafts.ts`. **Порядок выката:**

1. Actions → `migrate-barter-buy-limit` → Run workflow (идемпотентно, добавляет колонку)
2. деплой кода
3. Actions → `sync-prices` → Run workflow (тем же кроном синкаются бартеры)

До шага 3 колонка пустая, и `calcGpCurve` подставляет `FALLBACK_PURCHASES = 1`:
ёмкость ступеней занижена, курс смещён к предельному — то есть завышен, и предметы
выглядят менее выгодными, чем есть. После синка выправляется сам.

## Ограничения

- **Выборка мала.** Из ~329 предложений Рефа в расчёт попадают ~8 чисто-монетных и 2
  смешанных: у остальных награда вне барахолки и рыночной цены не имеет. Лега стоит на
  двух точках — это оценка, а не измерение, и в UI её надо показывать диапазоном.
  При медиане из двух значений одно предложение всегда выйдет выгодным, а второе —
  невыгодным ровно на ту же сумму: это свойство выборки, не баг.
- **Дробные `count`.** У большинства предложений число монет в API дробное
  (0.33, 124.08) — артефакт модели данных источника. Отсекается `Number.isInteger`.
- **База оценки.** `acquire` (цена покупки на барахолке) и `liquidate` (цена продажи
  минус комиссия) дают разные курсы; смешивать их в одном расчёте нельзя. Комиссию
  считать через `calcFleaFee` из `src/lib/barter-calc.ts` — своей формулы модуль
  не заводит.
- **Уровень лояльности.** Часть ассортимента закрыта; кривая строится с учётом
  `maxLevel`.
