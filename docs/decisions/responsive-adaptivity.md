# Адаптив портала по всем разрешениям (эпик)

## Цель
На каждом разрешении (320 → 4K) страница адаптируется **целиком и согласованно**: не «фулл-хд макет с полями по бокам» и не global zoom, а честная per-block вёрстка по брейкпоинтам. Философия wide-screen — **плотность** (V4DYA, 2026-08-17): элементы стандартного размера, но их БОЛЬШЕ в ряд; контейнер шире, +колонки. Шапка/футер/доки — по обычным брейкпоинтам, без масштабирования.

## Границы
- **В scope:** контейнер-колонка (`max-w-275`), `.tactical-grid` + `HubCard`, `HubNav`-семейство, `Header`, `Footer` (стримы/навигация), общие drawer'ы, страницы-списки предметов/квестов/видео.
- **НЕ трогаем:** интерактивные карты (`/eft/maps`, `/eft/questmap`, `/…/map`) — Leaflet со своей системой координат, отдельный трек. Аркадные canvas-игры. Логику/данные (только разметка и CSS).

## Решение (философия)
**Плотность, не пропорциональный масштаб.** На 2K/4K: контейнер расширяется, сетка добавляет колонки (`auto-fill` 160/gap28 остаётся базой), типографика — умеренный fluid `clamp`, но НЕ множитель ×1.33/×2. Отвергнуто: global `zoom` (см. Уроки).

## Контекст
- Файлы: `src/app/globals.css` (токены сетки/типографики, media-queries вне @layer), `src/components/ui/{GameCard,HubCard,Carousel}.tsx`, `src/components/*/HubNav*`, `src/components/layout/{Header,Footer,ConditionalLayout}.tsx`.
- `max-w-275` (=1100px) захардкожен на 30+ страницах как контейнер контента — единая точка расширения либо через утилиту, либо переопределением класса в globals.css (вне @layer, как было).
- Канон сетки/навигации: [[hubnav-canon]], [[cta-mobile]] (мобильные правила уже есть — <640 карточки 1-в-ряд, HubCard full-width).
- Токены: `--grid-max/-col/-gap`, `--type-*` (fluid clamp уже заведены в globals.css).

## Уроки (почему предыдущие попытки провалились)
1. **Global `zoom` на контент-`main`** — раздул контент, но шапку/футер/доки НЕ тронул → рассинхрон масштабов в одном экране. Zoom не реагирует на смысл блока (сетке нужны +колонки, а не «то же крупнее»). Откачено.
2. **Только расширение `max-w-275` (1600/2200) без реворка блоков** — контейнер шире, а HubNav/секции/футер остались фикс → страница адаптировалась наполовину, выглядело «сломанной сеткой».
   → Вывод: расширять контейнер МОЖНО (это и есть плотность), но одновременно каждый блок внутри должен уметь реагировать на новую ширину.

- [ ] **tactical-grid + HubCard** — auto-fill уже даёт +колонки; проверить спаны big/rectangle на широких (не растягиваются уродливо), выравнивание.
- [ ] **HubNav (3 вариации)** — левая/правая половины на широком: не растягивать текст на всю ширину, ограничить читаемую меру.

- [ ] Визуальная проверка на РЕАЛЬНЫХ разрешениях: 320, 768, 1368, 1920, 2560, 3840 — каждый блok из инвентаря отмечен.
- [ ] Нет горизонтального скролла ни на одном тире.

## Порядок исполнения
Блок за блоком, каждый закрывает петлю (правка → verify на разрешениях → отметка в инвентаре). Начать с контейнера + tactical-grid (ядро), затем HubNav, затем Header/Footer, затем страницы-списки и drawer'ы. НЕ делать всё одним коммитом — по блоку.

## Развилки (решить по ходу)
- Точные max-w контейнера на 2K/4K — подобрать визуально с V4DYA (черновик в матрице).
- Нужен ли верхний потолок плотности (напр. не более N колонок), чтобы карточки не мельчали в «стену».
- Container queries vs media queries для блоков, которые живут в разной ширине (drawer, вложенные сетки).

## Гарды
- Бюджет/масштаб: **большой** — множество файлов, но по блокам инкрементально.
- Ручное подтверждение: не требуется (только разметка/CSS, без БД/необратимого). Пуш в main — по блокам с verify.
