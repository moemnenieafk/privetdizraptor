# Колонка в schema.ts — НЕ аддитивная операция

**Статус:** ✅ сделано — порядок выката зафиксирован, грабли задокументированы.
**Затрагивает:** `src/db/schema.ts`, любые страницы с пререндером, `.github/workflows/migrate-*`
**Повод:** билд `c3f33bc` лёг на проде, разбор ниже.

## Что случилось

В `schema.ts` добавлено поле `buyLimit` в таблицу `barters`. Миграция — по нашей
обычной схеме: идемпотентный DDL за `CRON_SECRET` плюс `workflow_dispatch`. Считалось,
что добавление nullable-колонки безопасно и старый код о ней не узнает.

Билд упал:

```
column "buy_limit" does not exist   (42703)
Export encountered an error on /eft/barters/page
```

## Почему

Drizzle в `db.select().from(barters)` **без явного списка колонок** подставляет в SQL
все поля, описанные в схеме. Страница `/eft/barters` пререндерится на билде и читает
бартеры именно так. Колонки в проде ещё нет → запрос падает → падает весь билд.

Дальше замыкается круг: колонку добавляет роут миграции, роут миграции лежит в этом же
билде, билд не собирается. Ни задеплоить, ни мигрировать.

## Правило

> Добавление поля в `schema.ts` ломает прод-билд до применения миграции —
> везде, где таблица читается через `select()` без списка колонок на пререндере.

Отсюда обязательный порядок, три деплоя вместо одного:

```
1. деплой: роут миграции + воркфлоу, БЕЗ поля в schema.ts
2. Actions → migrate-* → Run workflow          (колонка появилась)
3. деплой: поле в schema.ts + код, который его использует
4. Actions → sync-*                            (колонка заполнилась)
```

Шаг 1 и шаг 3 — разные коммиты. Если поле и миграция уехали вместе, разрывать надо
коммитом, снимающим ссылки на поле (как `ac3a64d`), а возвращать — реверсом этого
коммита после шага 2.

## Как поймать заранее

- `grep -rn "select()\.from(<таблица>)" src/` — если есть хоть одно попадание в коде,
  который исполняется на билде, поле в схеме сломает сборку.
- Явный список колонок в `select({ ... })` иммунитета не даёт соседям: достаточно
  одного `select()` где-то ещё.
- Локальный `npx tsc --noEmit` это НЕ ловит — ошибка рантайм-SQL, а не типов.
  `next build` ловит, но только с доступом к прод-базе.

## Что не является причиной (проверено, чтобы не искать заново)

- `scripts/vercel-ignore.sh` отработал верно: `[vercel-ignore] есть изменения вне docs/ → BUILD`.
- `middleware.ts` API-роуты не перехватывает, matcher исключает только статику.
- Падение синка бартеров прод не роняет: в `/api/cron/sync-prices` он обёрнут в
  собственный `try/catch` как best-effort, цены синкаются отдельно. Но сбой при этом
  **тихий** — виден только в логах Vercel, воркфлоу рапортует зелёным.

## Симптом, по которому узнать это в следующий раз

Воркфлоу миграции падает с `HTTP 404`, а в теле ответа — HTML страницы 404 с RSC-payload
вида:

```
["game","api","d",null] → ["rest","cron/<имя>","oc",null]
```

Значит `api` подставился в динамический сегмент `[game]`, то есть роут-хендлера в
задеплоенном билде нет. Проверять надо не воркфлоу, а статус последнего билда.

Быстрая проба руками: открыть `<домен>/api/cron/<имя>` без заголовков.
`401 unauthorized` — роут живой. `404` — деплоя нет.
