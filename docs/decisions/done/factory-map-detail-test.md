### ⚠️ ГОЧА: строку `maps(factory-hd)` сносит каскад FK → метки исчезают

## Цель
Понять на примере Завода, **какой уровень детализации SVG-подложки карта тянет без лагов** при открытии/пане/зуме — и подтвердить, что маркеры ложатся на любую подложку. Играем **от обратного**: не «сколько деталей добавить», а «сколько деталей убрать, чтобы не грузило». Результат — «бюджет детализации» как норма для остальных карт.

## Контекст (что уже известно из кода — чтобы не гадать)
Три вопроса из постановки, и что по ним говорит архитектура ещё до теста:

1. **Лаги при открытии.** Подложка — это один тяжёлый `Factory.svg` (image-overlay в Leaflet). Leaflet перерисовывает его на каждом зуме/пане. Грузит не «красота», а **число узлов/path, фильтры и градиенты** внутри SVG. Это и меряем.
2. **«Подойдут ли маркеры».** Маркеры Завода приходят из **зеркала БД (`map_markers`)** и рисуются **отдельным pane ПОВЕРХ подложки**. Их позиция считается из мировых координат `(x,z)` через `transform`/`bounds`/`coordinateRotation` в `eft-map-config.ts` — **не из геометрии SVG**. Значит детализация арта на *попадание* маркеров не влияет вообще.
3. **«Если нет — перенести поверх подложки».** Это и есть **дефолтный режим** — маркеры всегда лежат своим слоем над артом. «Не подойти» они могут только если новый арт сдвинул привязку (см. гочи). Тогда — рекалибровка `transform`/`bounds` (как делали для Terminal по bbox спавнов) либо, в крайнем случае, ручные координаты как у статик-карт (Ледокол, `src/data/map-markers/`).

**Вывод-гипотеза до теста:** проблема — только в весе подложки. Маркеры отвяжутся от детализации by design. Тест это либо подтверждает, либо вскрывает рассинхрон привязки.

- **Файлы/папки:**
  - `public/images/maps/eft/Factory.svg` (+ зеркало Supabase `cta-media/maps/eft/factory.svg`)
  - `src/data/eft-map-config.ts` → блок `factory` (`transform`, `bounds`, `coordinateRotation`, `svgLayer: "Ground_Floor"`, этажи `Second_Floor`/`Third_Floor`/`Basement`)
  - Рендер: `src/app/eft/maps/[slug]/page.tsx` + `MapViewerClient` (Leaflet через `next/dynamic`, `ssr:false`)
  - Маркеры Завода: зеркало БД `map_markers` (карта интерактивная, НЕ `staticMap` → в `src/data/map-markers/` её нет)
- **Заметки:** [[maps-design-system]] (эталон/единый визуальный язык карт) · [[media-r2-webp-pipeline]] (растеризация в WebP — запасной путь для тяжёлого арта) · [[heatmap-loot-ev-dataset]] (гоча с overlayPane/z-index при слоях поверх арта)
- **Известные гочи:**
  - ⚠️ **Имена `<g id="…">` этажей не переименовывать** — Leaflet переключает этажи по ним (`Ground_Floor`, `Second_Floor`, `Third_Floor`, `Basement`). Перекрашивать/упрощать пути — можно; схлопывать/переименовывать группы — нельзя.
  - ⚠️ **viewBox/габариты SVG сохранять** — если новый арт сменил viewBox, поедет привязка маркеров (тогда править `bounds`/`svgBounds` в конфиге).
  - ⚠️ **В самой заметке не писать Tailwind-литералы в квадратных скобках** (`bg-[…]` и т.п.) — сканер контента ловит их из доков и роняет CSS (см. gotcha-tailwind-content-scan).

## Тайлы vs один WebP — порог (2026-08-09)
Опыт с тайлами есть, но в **обратную** сторону: [[map-stitch]] + `scripts/fetch-tiles.mjs` качают 256px-пирамиду с `assets.tarkov.dev` и **сшивают в один WebP** (референс для отрисовки, лицензии у растра нет → только локально). Генерации нашей пирамиды (картинка → тайлы) мы не делали.

Измеренные пределы (из `map-stitch/references/failure-modes.md`) — когда один файл перестаёт кодироваться в WebP:
- Порог **~150–210 Мпикс** (практический потолок 150). Завод z6 = 15664² = **234 Мпикс → `webpsave: unable to encode`**.
- Один WebP спокойно тянет **до ~8K** (8192² = 67 Мпикс), даже ~11K (121 Мпикс).

**Вывод для Завода:** тайлы не нужны. 142 м локации при 8K = ~58 px/м (= tarkov.dev z5, для обводки с запасом), один WebP/этаж ≈ несколько МБ, мгновенно. Тайл-пирамида (libvips `dzsave` → Leaflet `L.tileLayer`) оправдана только выше ~8K или на больших картах (Улицы/Лабиринт/Лаборатория) — и это переделка вьюера (`imageOverlay`→`tileLayer`). **Тайл 64px не брать — стандарт 256** (64 = ×16 запросов, грузит хуже).

Фикс: bounds через `map.unproject([0,H],maxZoom)` / `unproject([W,0],maxZoom)` (знак учитывается сам). Поле `tilePixelSize` в конфиге.
2. **Белые полосы — ДВА источника:** (а) добивка тайлов — холст был 16384×**16152**, sharp добивал нижний ряд белым; (б) `<rect fill="white">` прямо в вектор-SVG (4 в ground/basement, 2 в third). Лечение: V4DYA переэкспортировал квадрат **16384×16384** (PNG) + **4096×4096** (SVG) → сетка 64×64 без добивки; белые rect стрипаются из вектор-оверлея скриптом.

Проверено скриншотами: белых полос нет; глубокий зум = пиксель-детализация (покрышки/бочки/техника); переключение этажей (земля↔2-й↔тоннели) меняет тайлы+вектор синхронно; аспект квадратный — искажения нет. Вектор поверх приглушён `opacity:0.6` (тюнится).
- **Тюнинг под вопросом V4DYA:** прозрачность/цвет вектора (сейчас тёмные заливки дают затемнение растра), нужна ли strokes-only подача.

### ✅ Финал: полный растр в JPG, вектор не нужен (2026-08-09)
Инсайт при отладке «пустой карты»: первый растр-мастер содержал **только объекты/лут на тёмном фоне** — пол/стены жили в вектор-слое. Отсюда «дыры». Решение (выбрал V4DYA): **один полный JPG-мастер 16384² со всеми слоями** (пол+стены+объекты) → тайлы JPG.
- **JPG вместо WebP-с-альфой:** непрозрачные тайлы (фон #141416) → нет «пустых» прозрачных зон. Поле `tileExt` в конфиге (`'jpg'`); slice: `.jpeg({quality:88,mozjpeg:true})`.
- **Вектор-оверлей выключен** (`tileVector` не задан) — полный растр самодостаточен, в 16K и так резко. Код гибрида оставлен (гейт `cfg.tileVector`), можно вернуть как strokes-only.
- Проверено вживую (браузер): полная сплошная карта — пол+стены+техника, пиксель-детализация на зуме, этажи переключаются, полос/пустот нет. `tilePixelSize [16384,16384]`, `tileExt 'jpg'`.
- **Осталось:** прод-хостинг тайлов на R2 (сейчас `.gitignore`); маркеры из БД (этап B, калибровка под 16384²).

### ⚠️ ГОЧА: libvips google-layout = `{z}/{y}/{x}`, а не XYZ `{z}/{x}/{y}` (2026-08-09)
V4DYA заметил «стены не совпадают». Причина: sharp/libvips `tile({layout:'google'})` пишет тайлы **`{z}/{y}/{x}`** (строка Y, затем столбец X), а стандартный Leaflet-шаблон `{z}/{x}/{y}` (XYZ) → тайлы **транспонируются**, стены рвутся. Тихий баг: на обзоре выглядит правдоподобно.
- **Диагностика:** реконструкция карты из тайлов скриптом. Сборка по `{y}/{x}` = мастер 1:1; по `{x}/{y}` = каша. (Плюс грабля sharp: `.composite().resize()` в одной цепочке применяет resize ДО composite — реконструкцию делать двумя проходами.)
- **Фикс:** шаблон tileLayer → `/{z}/{y}/{x}.${ext}`. Проверено в браузере: совпало с мастером, стены непрерывны на всех зумах.

## Как тестируем (протокол)
1. Открыть `/eft/maps/factory`, DevTools → Performance.
2. Замер «до» на текущей детализированной подложке: время до интерактива (TTI), FPS при пане/зуме, пик памяти, вес `Factory.svg` (KB) и число узлов/path.
3. Прогнать 2–3 варианта упрощения (см. рычаги) и повторить замер — строим кривую «детализация → нагрузка».
4. Проверить маркеры и этажи на каждом варианте.

## Рычаги детализации (от тяжёлого к лёгкому)
- Упрощение путей (SVGO / simplify в Figma), удаление невидимой мелочи, объединение групп.
- Отказ от SVG-фильтров/градиентов/теней (самое дорогое на перерисовке).
- **Растеризация подложки в WebP** (есть пайплайн [[media-r2-webp-pipeline]]): арт становится растром, а маркеры остаются векторным слоем поверх — ровно «перенос маркеров поверх подложки», радикально дешевле по перерисовке.
- Пороги детализации по зуму (мелочь только на крупном зуме).

## Критерий готовности (детерминированный)
- [ ] Есть цифры «до/после»: TTI, FPS (пан+зум), память, вес SVG — в таблице в этой заметке.
- [ ] Маркеры визуально совпадают с объектами арта (спавны/выходы на своих местах) на всех вариантах.
- [ ] Этажи переключаются (id-группы сохранены).
- [ ] Зафиксирован **«бюджет детализации»** (потолок KB / узлов / без фильтров) как норма для остальных карт → в [[maps-design-system]].

## Развилки (твоя зона, реши по итогам замеров)
