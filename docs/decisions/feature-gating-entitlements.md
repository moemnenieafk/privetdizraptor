# Спринт: включаемые фичи по уровням пользователя (Entitlements + Feature Flags)

## Проблема
Гейтинг фич сейчас **разбросан и ad-hoc**: комменты чекают тир инлайн (`canWriteComments`), роли — свои предикаты (`canModerate`…), companion — свои. Нет единого места, где видно «какая фича кому доступна». А впереди — много **включаемых фишек** (напр. «выгодный бартер на карточке предмета», расширенные фильтры, история цен…), которые надо консистентно показывать/прятать/заманивать по уровню пользователя.

Нужна **единая декларативная система**: реестр фич + резолвер прав + режимы показа.

## Оси доступа (что определяет уровень)
1. **Auth** — аноним vs залогинен.
2. **Тир подписки** — `free / operative / veteran` (`subscription.server.ts`).
3. **Роль** — `user / editor / moderator / admin` (`roles.ts`).
4. **Ранг кармы** (компаньон, [[companion-gamification]]) — заработанные перки, ортогонально оплате.
5. **Ops-флаг** — глобальный рубильник/раскатка (вкл-выкл фичу для ВСЕХ, без деплоя).

## Модель
```
getEntitlements(user) → {
  authed, tier, role, karmaRank
}                                  // резолвится один раз (RSC)
can(ctx, featureKey) → 'show' | 'lock' | 'hide'   // + учёт ops-флага
```

### Реестр фич (декларативно, один файл)
```ts
// src/lib/features/registry.ts
FEATURES = {
  'item.barterHint':   { minTier: 'operative', gate: 'lock',  label: 'Выгодный бартер на карточке' },
  'item.priceHistory': { minTier: 'operative', gate: 'lock' },
  'item.advancedFilters': { minTier: 'operative', gate: 'show' },
  'progress.sync':     { requiresAuth: true,     gate: 'hide' },
  'companion.reader':  { requiresAuth: true,     gate: 'lock' },
  'comments.write':    { minTier: 'operative',   gate: 'lock' },
  'cms':               { role: 'canEditContent', gate: 'hide' },
  ...
}
```
Каждая фича объявляет: что нужно (auth/tier/role/karma) + **режим гейта**.

### Режимы гейта (UX-решение на фичу)
- **`show`** — доступна.
- **`lock`** — показываем, но заблокировано с апселлом («Оперативник») → **драйвит конверсию**. Для премиум-фич.
- **`hide`** — не показываем вовсе (админ-тулзы, приватное).

## Лестница уровней — что видит каждый
| Слой | Что доступно |
|---|---|
| **Аноним (без auth)** | Каталог, цены (зеркало), карты, квесты, вики — ЧИТАТЬ. Без прогресса/избранного/компаньона/персонализации. Премиум-фичи — как `lock`-тизеры. |
| **Free (залогинен)** | + синк прогресса (квесты/убежище/ачивки), избранное/трекинг, чтение комментов, **компаньон-ридер (вклад + карма)**, публичный профиль. |
| **Operative (платный)** | + премиум-карточки: **выгодный бартер на карточке**, крафт-профит, расширенные фильтры, история цен, запись комментов, приоритет. |
| **Veteran (выше)** | + всё Operative + экстра (больше слотов/лоадаутов, эксклюзив-косметика, ранний доступ к фичам). |
| **Ранг кармы** (ортогонально) | Косметика/бейджи/вес голоса, возможно «вкус» премиума (см. развилку в [[companion-gamification]]). |
| **Роли** (ортогонально) | editor → CMS; moderator → очереди модерации; admin → всё. |

## Ops-флаги (kill-switch / раскатка) — отдельно от прав
Фича видна если: **ops-включена И пользователь-имеет-право**. Ops-флаги — таблица `feature_flags` (редактируется в `/admin`, рантайм-тумблер без деплоя) ЛИБО конфиг. Нужны для: аварийного выключения, постепенной раскатки, A/B.

## Реализация (эскиз)
- `src/lib/features/registry.ts` — реестр.
- `src/lib/features/entitlements.ts` — `getEntitlements(user)` (реюз `getSubscription`, `roles.ts`, karma-rank).
- `src/lib/features/can.ts` — предикат `can(ctx, key)` (+ ops-флаг).
- **RSC:** `can()` на сервере — что рендерить/что НЕ слать клиенту.
- **Client:** `<Feature name="item.barterHint" fallback={<Upsell tier="operative"/>}>…</Feature>` — единый компонент показ/тизер.
- Ops-флаги: таблица + RLS (read-all) + CMS-тумблер (паттерн `migrate-*`).

## ⚠️ Критичные ограничения
1. **SSR/ISR:** права per-user = динамика. Аноним-базлайн держим **статикой/ISR** (не делать root dynamic — гочи [[db-egress-reduction]] / [[gotcha-tailwind-content-scan]]); персонализацию/гейтинг наслаивать **клиентски** или в динамических сегментах. Иначе убьём кэш и egress.
2. **Безопасность = на сервере:** для `lock`-фич сервер **НЕ должен слать премиум-данные** в клиент (иначе обход через DevTools). Гейт данных — серверный, UI-скрытие — вторично. `lock`-тизер получает только «заглушку», не данные.
3. **Консистентность:** все гейты — ТОЛЬКО через реестр (не инлайн-чеки), иначе снова разъедется.

## Разбивка спринта
- **F1 · Фундамент:** `getEntitlements` + `can` + реестр (перевести существующие инлайн-чеки: комменты/CMS/компаньон на реестр).
- **F2 · UI-примитивы:** `<Feature>` + `<Upsell>` (единый апселл-тизер под тир).
- **F3 · Ops-флаги:** таблица `feature_flags` + CMS-тумблер + `can()` их учитывает.
- **F4 · Первая премиум-фича через систему:** «выгодный бартер на карточке» (`item.barterHint`, operative, lock) — эталон-реализация.
- **F5 · Аудит:** пройтись по сайту, завести все гейты в реестр, задокументировать матрицу уровней.

## Открытые решения (V4DYA)
1. **Ops-флаги: БД-тумблер или конфиг?** (БД = рантайм без деплоя, но +таблица; конфиг = проще, но деплой на смену).
2. **Матрица «что где»:** финализировать таблицу уровней (какие именно фичи в operative vs veteran).
3. **Апселл-тон:** `lock`-тизер — насколько агрессивный (мягкий бейдж vs заметный CTA).
4. Связь с кармой: дают ли ранги кармы доступ к премиум-фичам (пересечение с [[companion-gamification]] развилкой про премиум-за-вклад).
