# Deep research: модель редактирования для CMS ЦТА

Развилка V4DYA: «где живёт редактирование — инлайн, /admin или оба? Выбрать лучший современный вариант».

## 1. Что считается стандартом в 2026

Рынок headless-CMS прошёл полный круг. Первое поколение (Contentful, Strapi, ранний Sanity) продавало «структурный контент через API», а редактор правил поля в отрыве от страницы. К 2024–2025 это стало стоить скорости, и лидеры выкатили **визуальное редактирование**; к 2026 отсутствие визуалки — минус на сделке.

Три модели визуального редактирования (общепринятая классификация):
1. **Inline на живой странице** — редактор открывает реальную страницу, у элементов появляются точки правки, изменения видны сразу (Storyblok, Sanity Visual Editing, Builder.io).
2. **Параллельная панель-превью** — форма слева, рендер справа (Payload Live Preview, Contentful Studio).
3. **Блочный редактор в стороне** — Notion-подобные блоки, страница собирается вне контекста.

Компромиссы: инлайн — самый дружелюбный, но технически самый требовательный; параллельное превью — надёжно для структурного контента; блочный — середина.

## 2. Что из этого подходит ЦТА

Наш контент делится на два класса, и это решает вопрос:

| Класс | Примеры | Природа |
|---|---|---|
| **Нарративный** | лор-статьи Кодекса, блог, разбор патча, описание мастер-класса | текст + медиа → **rich text / markdown** |
| **Структурный** | сюжетные гайды (дерево шагов → под-этапы → ветки-развилки, у каждого узла своё медиа), события, конфиги | **дерево данных**, WYSIWYG тут бессмысленен |

Из этого следует: **один редактор не закрывает обе задачи.** Нарратив — визуально-инлайн; структура — форма-конструктор с деревом.

## 3. Почему НЕ брать готовый headless (Payload/Directus/Strapi/Sanity)

- **Второй рантайм и вторая схема.** У нас Drizzle + Supabase, 25+ таблиц, RSC. Payload тянет свой слой БД и свою админку; Directus оборачивает существующую БД, но приносит чужой UI, чужую авторизацию и чужие роли поверх наших `profiles.role`.
- **Дубль дизайна.** NIGHTFALL — часть продукта. Админка на чужом UI-ките = второй визуальный язык и вечный рассинхрон.
- **Мы уже наполовину там.** `ArticleEditor` + `/api/admin/articles` (черновик/публикация/markdown) — это уже своя CMS, просто на один контент-тип.
- Решение E10 («своя лёгкая CMS на role=admin») подтверждается: отказ был правильным.

## 4. Почему инлайн для нас ДЕШЁВЫЙ (а не дорогой, как у всех)

Главная сложность инлайн-редактирования в индустрии — построить превью-мост между чужой CMS и чужим фронтом (postMessage-мосты, оверлеи, синхронизация). **У нас этой проблемы нет:** рендер контента — наши же компоненты (`CodexArticle`, `StoryWalkthrough`), редактор живёт в том же приложении, БД одна. Живая страница **и есть** превью.

Плюс Next.js даёт нативный механизм:
- **Draft Mode** (`draftMode()`): черновик виден только редактору, ISR-кэш для него обходится, publish не требуется для просмотра. Cookie `__prerender_bypass` httpOnly и подписана — подделать нельзя.
- **`revalidateTag`**: публикация мгновенно инвалидирует кэш нужного тега, без ребилда.
- Паттерн: `if (draft) → некэшированный запрос; else → unstable_cache(..., { tags: [...] })`.

## 5. Решение (рекомендация)

**Гибрид: инлайн-правка на живой странице + `/admin` как хаб.** Обосновано так:

- **Правка существующего** — инлайн, кнопка «✎» на странице для роли `editor`/`admin`: контекст, шрифты, сетка, мобильный вид — сразу настоящие. Черновик → Draft Mode → «Опубликовать» → `revalidateTag`.
- **Создание, поиск, массовые операции, статусы** — `/admin`: списки с фильтрами (черновики / опубликовано / автор / дата), кнопка «создать», удаление, медиа-библиотека, очередь модерации. Инлайн для этого не годится: нельзя «создать несуществующую страницу» на несуществующей странице.
- **Структурный контент (истории)** — конструктор дерева в `/admin` + инлайн-кнопка «править этот шаг» с самой страницы гайда (открывает нужный узел). Лучшее из двух.

Это ровно то, что делают лидеры: инлайн для контекста, дашборд для управления.

## 6. Редактор текста — что брать

Наши статьи уже хранят markdown (`bodyRu`). Рекомендация — **не тащить тяжёлый WYSIWYG сразу**:
- **Шаг 1 (сейчас):** markdown + живой предпросмотр компонентом рендера. Ноль зависимостей, ноль бандла, полностью совместимо с тем, что уже есть.
- **Шаг 2 (когда попросят редакторы):** **Tiptap** — headless-обёртка над ProseMirror, MIT-ядро, самый зрелый экосистемно; мы сами рисуем тулбар в NIGHTFALL, чужой UI не приходит. Альтернатива — Lexical (легче бандл, но круче кривая входа и меньше готовых расширений). BlockNote/Novel — Notion-стиль из коробки, но приносит свой UI-слой → конфликт с дизайн-системой.
- Платные (TinyMCE/CKEditor/Tiptap Cloud) — не нужны: коллаборативное редактирование нам не требуется, редакторов единицы.

## 7. Роли

`UserRole` расширяется до `user | editor | moderator | admin`:
- **editor** — пишет и публикует контент (кодекс, истории, блог, мастер-классы, разборы патчей). НЕ трогает каталог предметов, роли, настройки.
- **moderator** — модерация «Связи» (уже есть).
- **admin** — всё, включая каталог и выдачу ролей.
Гейт: `canEditContent(role) = editor | admin`. Роут `set-role` расширить на `editor`.
