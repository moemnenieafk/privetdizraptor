# Проекция игровых координат в SVG

Полный контракт — `docs/maps/SPEC-DRAWING.md` §1. Здесь только то, что нужно
при сшивке и при разборе жалоб «маркеры не туда».

## Живая реализация

`src/data/eft-map-config.ts` — конфиг, `src/components/features/maps/MapViewerClient.tsx`
— сборка CRS. Оба рабочие. **Читать их прежде, чем что-то менять.**

Конвейер: координаты маркера подаются как `latLng(z, x)` — `x` в долготу
(горизонталь), `z` в широту (вертикаль). Дальше поворот на `coordinateRotation`,
затем `L.Transformation(t[0], t[1], -t[2], t[3])`. Подложка кладётся
`imageOverlay` по тем же `bounds` через тот же конвейер, поэтому картинка и
маркеры совмещаются автоматически.

## Главное заблуждение

**`transform` — не «метры в пиксели viewBox».** Он отображает в собственное
CRS-пространство Leaflet.

На Customs подложка занимает в этом пространстве 255.6 × 130.0 единиц при
viewBox 1062.5 × 535.2. Соотношение сторон совпадает (1.97 против 1.985),
абсолютные числа — нет.

Если подставить игровые координаты в `transform` и сравнить результат с
размерами viewBox, маркеры «займут 13–36% холста» и покажется, что проекция
сломана. Это артефакт измерения: результат в пространстве 255×130 меряется
линейкой на 1062. Проверять надо целиком собранный конвейер, а не одну его
ступень.

## Соответствие осей

**Ширина холста отвечает игровой оси X, высота — оси Z.**

Четыре независимых подтверждения:

1. `ll(p) = [p.z, p.x]` в живом коде — `x` идёт в горизонталь;
2. `SpawnPointParams` из базы SPT: на Customs размах по X равен 999 м при
   `bounds`-размахе 1070, по Z — 441 при 544;
3. `Bounds` из DynamicMaps с явно названными осями;
4. `bounds` из `maps.json`.

Совпадение на пяти картах из пяти.

В ревизии `SPEC-DRAWING.md` до 29.07.2026 было записано обратное. Размеры
холстов при этом были верные — перепутаны только подписи осей.

## Развилка контрактов

Существующие SVG Shebuka нарисованы в повёрнутом кадре, `transform` под них
откалиброван. При перерисовке карты выбирается одно из двух — **на весь набор,
не по карте**:

**Вариант А.** Остаться в схеме Shebuka, калибровать `transform` под новые
размеры. Код не трогается, меняются четыре числа на карту.

**Вариант Б.** Перейти в игровой кадр: X по горизонтали, Z по вертикали,
Z растёт вверх, холст размером ровно с `bounds`. Тогда `coordinateRotation: 0`,
`transform` тождественный, и проекция сводится к:

```
svgX = (gameX - bounds.xMin) * viewBoxW / boundsWidth
svgY = (bounds.zMax - gameZ) * viewBoxH / boundsHeight
```

Плюс варианта Б — исчезает исключение «при повороте 90/270 оси меняются
местами» (Factory и Labs у Shebuka развёрнуты на 90°). Минус — конфиг и
калибровка переделываются целиком.

## Оверлеи подписей из пака нерабочие

`labels/overlays/*.svg` пишут сырые игровые координаты прямо в `x`/`y` при
`viewBox`, начинающемся с нуля. Всё отрицательное оказывается за холстом —
примерно 190 подписей из 303:

| карта | вне холста |
|---|---|
| Interchange | 55 из 77 |
| Streets | 28 из 46 |
| Reserve | 24 из 27 |
| Lighthouse | 21 из 22 |
| Customs | 17 из 24 |

Пересобирать с переносом в координаты холста. Знак поворота подписи при этом
инвертируется: отражение оси Y меняет направление вращения.
