# Ассеты: у пользователей из России не грузятся карты и картинки (Cloudflare R2)

- **Раздел:** весь сайт — доставка ассетов (иконки предметов, арт/тайлы карт, медиа, баннеры сезонов)
- **Компонент:** база ассетов на Cloudflare R2 (`NEXT_PUBLIC_ICON_BASE_URL` / `mapAssetBase`, публичный `*.r2.dev`) `~вывод`
- **Что не так:** у пользователей из России не прогружаются все карты и картинки — ассеты лежат на R2 (Амстердам) и не доходят до RU-аудитории.
- **Ожидалось:** картинки и карты грузятся у российских игроков (основная аудитория портала).
- **Требование автора:** найти решение и реализовать **фоллбэк** на загрузку ассетов, изначально находящихся на R2 Cloudflare.

> исходное сообщение (as-is):
> #баг
> Все карты и картинки не прогружаются для жителей России. Найти решение и реализовать фоллбэк на загрузку ассетов которые изначально находятся на R2 Cloudflare - Амстердам

## ✅ Блокер выката снят (2026-09-04, 07:44 UTC)

Делегирование почищено V4DYA у REG.RU → зона активировалась → `cdn.cta.quest` привязан
к бакету по API с первой попытки. Домен проверен живьём: иконка предмета и тайл Таможни
отдаются `200`, `Cache-Control: immutable` сохранён, SSL `active`, и — главное — адрес
**`188.114.97.1`**, тот же «хороший» пул CF, на котором работает сам сайт. Ровно тот
исход, ради которого выбирался кастомный домен.

Кэш на краю работает из коробки: `cf-cache-status: HIT`, `Age` растёт. Cache Rule НЕ нужен.

⚠️ Ложная тревога, стоившая лишнего правила в конфиге: сначала было объявлено, что край не
кэширует (`cf-cache-status: DYNAMIC` на всех ассетах). Это артефакт метода — замер шёл через
`curl -I`, то есть HEAD, а Cloudflare кэширует GET. Настоящий GET с самого начала отдавал
`HIT`. Заведённое по ошибке правило удалено, конфиг возвращён в исходное состояние.
**Мерить кэш только реальным GET** (`curl -s -o /dev/null -D - URL`), HEAD врёт.

## 🔴 Блокер выката: расщеплённое делегирование NS (найдено 2026-09-04)

Привязать `cdn.cta.quest` не даёт ни панель, ни API — обе выдают `The specified zone id is
not valid` (код 10051). Причина: **зона `cta.quest` не активирована в Cloudflare**, а R2
Custom Domain требует активной зоны.

Почему не активируется — в реестре `.quest` (RDAP CentralNic) делегировано **ШЕСТЬ** NS:

```
carol.ns.cloudflare.com     ← Cloudflare
rommy.ns.cloudflare.com     ← Cloudflare
ns1.timeweb.ru              ← хвост от Timeweb
ns2.timeweb.ru
ns3.timeweb.org
ns4.timeweb.org
```

Cloudflare активирует зону только при ИСКЛЮЧИТЕЛЬНОМ делегировании на свои серверы.
Смешанное — вечный `pending`, «Check nameservers» не помогает (проверено: статус лишь
переполз `moved` → `pending`). DNSSEC ни при чём — DS-записи у родителя нет.

⚠️ **Это не только блокер выката, это самостоятельный баг.** NS Timeweb отдают по
`cta.quest` чужие адреса: `85.193.93.93` (на запрос сайта — HTTP 409, не наш сайт) и
`217.78.234.130`, вместо VPS `201.51.20.217`. Резолверы выбирают NS из делегирования
произвольно → часть пользователей уезжает на мёртвый хост. Симптом «сайт не работает»,
не связанный с картинками.

**Вылечено у регистратора (REG.RU):** в делегировании оставлены только `carol.ns.cloudflare.com`
и `rommy.ns.cloudflare.com`. Зона активировалась за минуты.

Откуда взялись лишние NS: Timeweb требовал добавить их, чтобы завести почту на домене.
Почту в итоге не завели («невозможен перенос домена в их зону»), а NS остались и две недели
ломали зону. На будущее: **почта на своём домене — это MX-записи, а не владение зоной**;
переносить домен ради почты не нужно, MX добавляются прямо в Cloudflare DNS.

⚠️ Методическая ошибка, не повторять: `nslookup -type=NS cta.quest` отдаёт ответ СО СТОРОНЫ
ДОЧЕРНЕЙ зоны (сами CF-серверы рапортуют только о себе) и показал два NS из шести — на
этом основании делегирование было ошибочно объявлено корректным. Истину про делегирование
даёт только реестр: `curl https://rdap.centralnic.com/quest/domain/cta.quest`.

## Диагноз (2026-09-03, подтверждён замером)

**Причина: ТСПУ блокирует домен `r2.dev` по SNI.** Не «R2 недоступен из РФ» и не «задушен
IP-диапазон Cloudflare». Установлено методом исключения:

- `cta.quest` и `pub-….r2.dev` оба обслуживаются Cloudflare. У тех же RU-юзеров первый
  работает (вёрстка, тексты, навигация на месте), второй — нет. Единственное различие
  на пути через ТСПУ — **имя хоста в SNI**.
- Cloudflare сам раздаёт РФ альтернативные адреса (`8.47.69.0`, `8.6.112.6` вместо
  `104.18.x`) — версия «режут диапазон `104.16/12`» опровергнута.
- Замер check-host.net с трёх RU-узлов (Москва ×2, СПб): `r2.dev` отвечает 200 за 0.15–0.24 с.
  Все три — **хостинговые AS**, они не за абонентским ТСПУ; замер подтверждает, что
  маршрут до CF цел, и локализует проблему в абонентских сетях.
- Тот же класс блокировки, что накрыл `*.workers.dev` (у нас на нём висит
  `gemini-proxy.cta-quest.workers.dev` — для RU он тоже мёртв, см. «Хвосты»).

⚠️ Ложный след, стоивший бы дня: с машины V4DYA `r2.dev` отвечает нормально — но её трафик
уходит **через Финляндию** (`45.144.53.136`, `colo=HEL`). Ни разработчик, ни агент не видят
RU-картину; проверять только с выключенным VPN.

## Решение: кастомный домен `cdn.cta.quest`

Меняется имя хоста при той же инфраструктуре CF — бьёт точно в причину. Бакет `cta-media`
привязывается Custom Domain в зоне `cta.quest` (сама зона у RU-юзеров доступна, чем и
доказана работоспособность подхода). Бонусом снимается rate-limit `r2.dev`.

Отвергнуто: проксирование через свой origin (гнало бы 55 000 тайлов через амстердамский
VPS без нужды) и клиентская фолбэк-цепочка (стрельба вслепую до диагноза; все 8 точек
резолва и так читают одну env-переменную, отдельный резолвер не требуется).

### Сделано в коде
- `.env.local` — `NEXT_PUBLIC_ICON_BASE_URL` и `NEXT_PUBLIC_MAP_TILE_BASE_URL` → `https://cdn.cta.quest`
- `next.config.ts` — `images.remotePatterns`: добавлен `cdn.cta.quest`, `**.r2.dev` оставлен как путь отката
- `MapViewerClient.tsx` — обработка `tileerror`: при блокировке CDN карта больше не пустая
  молча, показывается плашка. Порог 4 промаха, сброс на первом успешном тайле.
- `scripts/r2-host-migrate.ts` — разовая миграция абсолютных URL, зашитых в БД
  (`media_assets.url`, тела статей). Скан по всем text/json-колонкам public-схемы,
  запись только по `--apply`.

### Требует V4DYA (у агента нет доступа)
1. **REG.RU (СНАЧАЛА ЭТО):** в делегировании `cta.quest` оставить только два CF-сервера,
   удалить четыре `*.timeweb.*` — см. блок «Блокер выката» выше. Без этого зона не
   активируется и привязка домена невозможна в принципе.
2. **Cloudflare-панель (после активации зоны):** R2 → `cta-media` → Settings →
   Custom Domains → Connect `cdn.cta.quest`.
3. **Coolify:** `NEXT_PUBLIC_ICON_BASE_URL=https://cdn.cta.quest` + **полная пересборка**.
   `NEXT_PUBLIC_*` вшивается в бандл на этапе билда, и `next.config.ts` читает её там же —
   смены переменной без редеплоя недостаточно.
4. **SSH-туннель** (`bash ~/cta-provision/dev.sh`) — для миграции URL в БД.
5. **Верификация с выключенным VPN** — единственный доступный нам RU-канал наблюдения.

### Границы
- `pub-….r2.dev` остаётся включённым: откат — одна переменная + пересборка.
- Единый `assetUrl()`-резолвер не делался (8 точек читают одну env) — записано в долг.
- `gemini-proxy.cta-quest.workers.dev` мёртв для RU по той же причине, но вызывается
  серверно/локально — вне скоупа этого бага.

**Связь:** ассеты на R2 вынес коммит `fceaba09` (медиа, в т.ч. `seasons/`); ср. баг
hero-баннеров [[bugs/2026-08-28-1158--perks-constructor-hero-images.md]] — тот же R2-слой,
но другая причина (`next/image` мимо редиректа).
